# DSH Crew v0.3 Architecture Roadmap

Status: proposed / implementation starting
Baseline: `main@d7c6ad8d9b12a767940ee20f708d20daf0b2986e`

## Why v0.3 exists

v0.2 closed the runtime-hardening loop: shared blocking/async workflow semantics, cancellation, timeout, escalation, reviewer flow, candidate capture, worktree isolation, provider/model priorities, and real-environment coverage across DeepSeek/OpenCode Go including MiMo and Qwen.

The main architectural risk now is no longer worker correctness in one process. It is **cross-component drift**: the MCP process, the DSH Hub plugin snapshot, persisted Crew config, DSH provider catalog, and installed package identity can all evolve independently. v0.3 should make those boundaries explicit and observable before adding adaptive routing.

## Review findings

### P0 — Runtime Compatibility Contract

Current state:

- MCP server reports version `0.2.0` in `src/server.mjs`.
- Package identity remains `0.1.0-rc.1` in `package.json`.
- Hub `/_dsh/dsh-crew/ping` reports only `{ ok, service }`.
- `src/hub-client.mjs` treats any responding `dsh-crew-hub` as compatible.
- Real-environment testing observed a new MCP/runtime talking to an older installed Hub plugin snapshot (`80db87a`). That skew was only discovered by manual diagnosis.

Risk:

A new MCP can unknowingly call an older Hub that accepts the HTTP shape but lacks newer workflow semantics. Failures then look like routing, policy, or model bugs instead of compatibility problems.

v0.3 direction:

1. Introduce one shared runtime identity module.
2. Separate package version from a small integer/API protocol version.
3. Hub ping returns protocol version, component version, and a capability list.
4. MCP probes and records Hub compatibility instead of only reachability.
5. Required capabilities are checked before using features that depend on them.
6. Config/status output exposes compatibility diagnostics without leaking secrets.
7. Old Hub behavior must fail clearly or downgrade intentionally; never silently pretend to be fully compatible.

Exit criteria:

- A stale Hub is distinguishable from an unreachable Hub.
- New MCP + old Hub produces a deterministic diagnostic code.
- Tests cover compatible, old/missing-protocol, and capability-missing Hub responses.

### P1 — Config Authority Cleanup

Current state:

v0.2 introduced canonical `worker`, `review`, and `execution` shapes while retaining legacy Flash/Pro fields for migration and UI compatibility. Multiple paths still read/write the legacy fields and derive the canonical view on demand.

Risk:

The longer both representations stay writable, the more likely they diverge. The project already needed explicit resynchronization logic around fields such as `tier_policy`, collaboration mode, role state, priorities, and presets.

v0.3 direction:

- Define a single persisted schema version.
- Treat legacy fields as import/migration inputs, not parallel authorities.
- Make writes canonical first; render compatibility views from canonical state.
- Add schema validation and migration diagnostics.
- Preserve explicit user choices; migrations must never silently broaden permissions or provider access.

Exit criteria:

- One write path owns each effective behavior.
- Legacy compatibility is deterministic and covered by migration fixtures.
- Config reports include schema version and migration status.

### P1 — Dynamic Runtime Controls

Current state:

`max_parallel` is captured when `buildMcpWorkflowRuntime()` creates the runtime. Updating the global setting does not change the active runtime's concurrency limiter until a new MCP process/session is created.

v0.3 direction:

- Make concurrency policy read from a live getter or an explicit runtime update API.
- Clearly label settings as either live, next-job, next-session, or restart-required.
- Apply the same lifecycle labels in Settings UI and `dsh_worker_config` output.

Exit criteria:

- Changing supported live controls changes subsequent dispatch behavior without process restart.
- Every non-live setting clearly states its activation boundary.

### P1 — Model Selection Trace

Current state:

Jobs record selected provider/model and `selection_source`, but the full decision chain is not first-class: which policy candidates were considered, which were unavailable, whether a legacy class hint changed the pool, and why Harness Default won.

v0.3 direction:

Record a sanitized model-selection trace per attempt:

- role / logical attempt
- model-class hint if present
- policy strategy
- candidate order
- skipped candidates + safe reason codes
- selected provider/model
- selection source
- fallback/escalation reason

No credential values or provider secrets may enter the trace.

Exit criteria:

A user can answer “why did this attempt use this model?” from `dsh_worker_result` / job metadata without reading logs.

### P2 — Provider/Catalog Safety Diagnostics

Real-environment remediation showed that a local DSH `opencode-go.models` override reduced the effective provider catalog from the built-in set to two models, hiding MiMo/Qwen. Crew correctly reflected the effective Harness catalog; the root cause was external provider configuration.

v0.3 direction:

- Keep Harness/DSH authoritative for provider registration and protocol metadata.
- Do not mirror or hardcode third-party model catalogs in Crew.
- Surface catalog-health hints only when they can be derived safely from effective data or explicit DSH metadata.
- Prefer upstream/provider diagnostics over Crew guessing.

Exit criteria:

Crew does not mask provider configuration mistakes with a competing shadow catalog.

### P2 — Adaptive Routing

Adaptive routing is intentionally after compatibility, config authority, and tracing.

Potential inputs:

- recent attempt success/failure
- timeout rate
- observed latency
- explicit user priority
- role and task class
- provider availability

Non-goals for the first v0.3 implementation:

- no automatic cost optimization without explicit pricing data
- no hidden provider switching that bypasses configured priorities
- no credential or quota scraping
- no model-quality claims based only on model names

Exit criteria for an initial experiment:

- deterministic baseline remains available
- adaptive mode is opt-in
- every adaptive decision is explainable via the selection trace

### P2 — Release / Environment Matrix Automation

Current coverage is strong but assembled from CI plus real-environment reports.

Target matrix:

- Linux deterministic suite
- Windows path/Git/worktree regressions
- macOS smoke when infrastructure is available
- Hub compatibility handshake
- provider catalog smoke
- DeepSeek Flash/Pro
- OpenCode Go MiMo/Qwen
- reviewer pipeline
- cancellation/timeout/escalation
- standalone official path when an authorized key is available

The matrix should report PASS / FAIL / BLOCKED / SKIP with a reason code, not collapse unavailable credentials into failures.

## Implementation order

### Phase A — Compatibility foundation

1. Runtime identity + Hub capability handshake.
2. Compatibility diagnostics in MCP config/status.
3. Tests for stale Hub / capability mismatch.

### Phase B — Configuration authority

1. Persisted schema version.
2. Canonical write path.
3. Legacy import/migration fixtures.
4. Activation-boundary labels for settings.

### Phase C — Observability and live controls

1. Model selection trace.
2. Dynamic `max_parallel`.
3. Job/event diagnostics surfaced in UI/MCP result.

### Phase D — Routing experiments

1. Opt-in adaptive routing policy.
2. Provider-health sampling from job outcomes.
3. Release matrix automation.

## First implementation task

**Runtime Compatibility Contract** is the first v0.3 source change.

Minimum patch scope:

- shared runtime/protocol identity constants
- enriched Hub ping response
- Hub probe result with reachability + compatibility
- deterministic compatibility error codes
- unit tests

Do not change worker routing, model policy, credentials, package release/versioning, CI workflow, or provider configuration in the first patch.

## Definition of v0.3 architecture success

v0.3 is successful when DSH Crew can explain, before dispatch and after an attempt:

1. **What component am I talking to?**
2. **Is it compatible with this runtime?**
3. **Which config is authoritative?**
4. **Why was this model selected?**
5. **Which settings are live versus restart/session scoped?**
6. **What exactly failed: policy, compatibility, provider availability, runtime, or task verification?**

Only after those questions are deterministic should routing become more adaptive.
